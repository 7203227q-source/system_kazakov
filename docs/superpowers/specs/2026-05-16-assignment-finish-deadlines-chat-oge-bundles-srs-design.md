# Дизайн: завершение варианта, дедлайны, чат, ОГЭ-связки 1–5, SRS счётчик/ETA

Дата: 2026-05-16

## Контекст

Есть несколько связанных UX/данных проблем в учебной платформе:

1) У ученика по нажатию «Завершить вариант» вариант иногда не завершается и не попадает в решённые.  
2) Нужно визуально выделять варианты, срок которых подходит к завершению, и показывать дату дедлайна.  
3) У репетитора периодически “пропадает” поле ввода/отправки сообщений в чате.  
4) Для ОГЭ блока 1–5 при генерации варианта не всегда к задаче №1 подтягиваются связанные №2–№5 из-за невалидных/неполных связок в БД.  
5) В режиме повторения (SRS) нужно показывать “осталось задач” и оценку времени до окончания.

## Цели

- Вариант должен завершаться предсказуемо при нажатии «Завершить вариант».
- Для вариантов с 2-й частью: не блокировать завершение навсегда, а требовать подтверждение, если нет фото по некоторым задачам 2-й части.
- На дашборде ученик должен видеть дедлайны и “скоро дедлайн” (порог: 1 день).
- В чате репетитора поле ввода не должно “исчезать молча”; при проблеме выбора диалога должно быть явное состояние.
- Генератор должен выбирать только валидные связки ОГЭ 1–5; отдельно нужен безопасный инструмент “почистить” БД.
- В SRS показывать счётчик “сегодня повторить” и ETA.

## Не-цели

- Менять алгоритм оценки/проверки 2-й части, ИИ-проверку или правила начисления XP.
- Делать сложный календарь дедлайнов (достаточно бейджей/даты и сортировки).
- Полноценный “мессенджер” с WebSocket: остаёмся в текущей модели (polling/fetch).

## Текущее поведение (по коду)

- Завершение варианта происходит в `student_solve_assignment` и зависит от `POST action=finish`. Сейчас `action` выставляется инлайновым JS, что делает поведение хрупким (Enter/автосабмит/сломанный JS → `action` отсутствует).
- Для 2-й части есть серверная блокировка завершения: если по любой extended-задаче нет `submission.image_url`, завершение запрещается (redirect обратно).
- На странице решения варианта нет универсального блока отображения `messages`, поэтому предупреждение может “не быть видно” пользователю.
- В чате поле ввода рендерится только при наличии `active_dialog` (если по какой-то причине попали на `/chat/` без диалога, UI выглядит как “пропало поле ввода”).
- Для ОГЭ 1–5 генератор подтягивает задачи по `bundle_code`, но не проверяет, что bundle полный (1..5 присутствуют ровно по одному).
- В SRS режим тренажёра выбирает только одну due-задачу и не показывает, сколько ещё осталось.

## Предлагаемые изменения

### 1) Завершение варианта (включая 2-ю часть)

#### UX

- Кнопки внизу формы решения варианта становятся “настоящими submit”:
  - `name="action" value="postpone"`
  - `name="action" value="finish"`
  Это устраняет зависимость от инлайнового JS для критического сценария.

- Если ученик нажал «Завершить», и обнаружены задания 2-й части без фото:
  - Показываем предупреждение на этой же странице (без редиректа), со списком задач (например: “Задача 14, 16: нет фото”).
  - Показываем подтверждение вторым действием:
    - Кнопка “Вернуться и загрузить фото” (просто закрыть предупреждение/оставить на странице).
    - Кнопка “Завершить всё равно” (submit с `name="force_finish" value="1"` + `action=finish`).

#### Backend

- При `POST action=finish`:
  - Собираем `missing_part2`: extended-задачи, у которых нет `submission.image_url`.
  - Если `missing_part2` не пуст и `force_finish != 1`:
    - Рендерим страницу решения варианта с:
      - списком `missing_part2`
      - флагом `needs_force_finish=true`
      - выставленным `action=finish` (чтобы второе подтверждение было тем же сценарием)
    - Не меняем `assignment.is_completed`.
  - Если `force_finish == 1`:
    - Разрешаем завершение.
    - Для missing-задач гарантируем, что есть `Submission` (уже есть `get_or_create`), и оставляем `primary_score=0`, `tutor_primary_score=None`, `is_correct=None` (или `False`) — чтобы итоговый подсчёт был корректный (0 баллов).

#### Сообщения

- На странице решения варианта нужен общий блок отображения `messages` (warning/success), чтобы любая серверная подсказка была видна.

#### Критерии готовности

- Нажатие «Завершить вариант» без JS (Enter/disabled JS) всё равно корректно завершает (если нет 2-й части без фото) или приводит к экрану подтверждения (если есть).
- При наличии missing фото:
  - первый клик — предупреждение и список задач
  - второй клик (подтверждение) — завершение варианта

### 2) Дедлайны: подсветка “срок подходит к завершению” и отображение дат

#### UX (дашборд ученика)

- В списке нерешённых вариантов показывать дату `due_date` (если задана).
- Бейджи:
  - “Просрочено” если `due_date < today`
  - “Срок сегодня/завтра” если `due_date <= today + 1 day`
- Сортировка нерешённых: варианты с ближайшим `due_date` сверху (null внизу).

#### API/данные

- Если список нерешённых обновляется через API (например, “обновить карточку”), API должен отдавать:
  - `due_date` в удобном для UI формате
  - `due_status` (none/soon/overdue) или достаточно `due_date` + `today` на фронте.

### 3) Чат: “пропадает поле ввода”

#### Причина в текущем дизайне

Поле ввода рендерится только если есть `active_dialog`. Если по какой-то причине пользователь оказался на `/chat/` без активного диалога (или по невалидной ссылке), UI выглядит “сломано”.

#### UX

- Если диалогов нет: показывать явное empty-state (“Нет доступных диалогов” + причина/что сделать).
- Если диалоги есть, но `active_dialog` не выбран:
  - автоматически выбрать первый диалог и показать его.
- Если пользователь перешёл по ссылке на недоступный диалог:
  - показать сообщение “Диалог недоступен” и вернуть к списку диалогов, сохраняя видимость UI.

#### Backend

- `chat_index` должен выбирать `active_dialog = dialogs[0]` если `dialogs` не пуст.
- `chat_dialog` при неразрешённом `user_id` должен не просто редиректить, а ещё установить `messages.warning(...)` (или флаг в query), чтобы пользователь понимал причину.

### 4) ОГЭ: связки 1–5, валидность и чистка базы

#### Проблема

Генератор выбирает `bundle_code` и подтягивает задачи с номерами 1..5 по этому `bundle_code`, не гарантируя полноту набора.

#### Генерация (гарантия связности)

- При выборе bundle-кодов считать валидными только те `bundle_code`, где:
  - среди задач с `task_type.number in [1..5]` ровно 5 задач
  - присутствуют все номера 1..5 ровно по одной
- Использовать только валидные bundle-коды для “блоков 1–5”.
- Если валидных связок недостаточно под запрошенное количество:
  - добирать оставшееся обычными (несвязанными) задачами по тем же правилам, что сейчас
  - либо явно предупреждать репетитора в UI (предпочтительнее), что “валидных связок меньше, чем запрошено”.

#### Чистка (безопасный режим)

Добавить management-команду (dry-run по умолчанию), которая:
- Находит все “плохие” bundle-коды (не соответствующие критериям выше).
- В безопасном режиме сбрасывает `bundle_code=NULL` у задач 1..5 с плохими bundle-кодами (не удаляя задачи и историю).
- В отчёте печатает количество найденных “плохих” связок и количество затронутых задач.

Отдельно (только при отдельном подтверждении): “жёсткий режим” удаления возможен, но только для задач, которые:
- не используются в `Assignment.tasks`
- не имеют `Submission`, `TaskLog`, `SpacedRepetition` и т.п.

### 5) SRS: “осталось задач” и ETA

#### UX

На странице повторения (`mode=srs`) показывать:
- “Сегодня повторить: N”
- “После этой останется: N-1” (если есть текущая задача)
- “≈ X минут” (ETA)

#### Подсчёты

- `N` = `get_due_tasks_for_student(user).count()`
- ETA:
  - Пытаемся взять среднее/медиану `TaskLog.time_spent` по ученику (последние N логов без аномалий).
  - Fallback: среднее по всем ученикам.
  - `ETA = due_count * avg_seconds` (округление до минут).

## План тестирования (уровень требований)

- Assignment finish:
  - POST без JS (прямой submit) завершает вариант.
  - При missing 2-й части: первый submit показывает подтверждение, второй завершает.
- Deadlines:
  - бейдж “срок завтра/сегодня” появляется за 1 день
  - сортировка по due_date
- Chat:
  - `chat_index` выбирает первый диалог, поле ввода видно при наличии диалогов
  - переход по невалидной ссылке даёт понятное сообщение и не приводит к “пустому сломанному UI”
- OGE bundles:
  - генератор использует только валидные bundle_code
  - команда чистки корректно определяет bad bundles и безопасно “отвязывает”
- SRS:
  - счётчик due-задач и ETA отображаются в UI и корректно обновляются.

## Риски и откат

- Изменение поведения finish для 2-й части: важно не потерять данные; подтверждение должно быть серверным (не только JS).
- Чистка bundle_code: безопасный режим не удаляет данные, откат прост (можно восстановить по резервной копии БД; жёсткий режим не применять без бэкапа).
