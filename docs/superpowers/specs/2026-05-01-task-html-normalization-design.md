## Контекст

В «банке заданий» часть задач отображается «столбиком»: перенос строки происходит после формул и даже после буквенных обозначений (например, `ABC`, `BB₁`). Причина — «сломанная» HTML-разметка в `TaskVariant.content/solution` (частые `<br>`/разбиение текста на слишком короткие строки).

Цель: нормализовать контент так, чтобы он корректно читался в UI, при этом не сломать валидное форматирование (списки, таблицы, формулы, картинки).

## Цели

- Исправить отображение уже импортированных задач (разовая миграция данных на уровне контента).
- Предотвратить повторное появление проблемы для новых импортов (нормализация при импорте).
- Сохранить форматирование там, где переносы строк нужны намеренно.

## Не цели

- Полная реконструкция исходного HTML до «идеального» семантического вида.
- Автоматическое переписывание формул/MathML/MathJax.
- Вмешательство в рендеринг на фронте «глобальными CSS-хаком» (это ломает корректные задачи).

## Наблюдения по текущему коду

- Контент задач хранится в `TaskVariant.content` и выводится как `|safe` в шаблонах банка заданий.
- Импорт из CSV уже обрабатывает картинки через `download_and_replace_images(...)`.

## Подход (вариант A — выбран пользователем)

### 1) Нормализация HTML при импорте

В пайплайне импорта добавить нормализацию:

- `processed_content = download_and_replace_images(...)`
- `normalized_content = normalize_task_html(processed_content)`
- сохранять `normalized_content` в `TaskVariant.content`

Аналогично для `solution`.

### 2) Разовая чистка уже загруженных задач

Добавить management-команду, которая:

- итерирует `TaskVariant` (опционально по `--limit`, `--ids`, `--theme`)
- применяет `normalize_task_html` к `content` и `solution`
- сохраняет только если контент изменился
- поддерживает `--dry-run` (показывает сколько записей изменилось бы)

## Алгоритм normalize_task_html (эвристический)

### Общая идея

«Столбик» чаще всего возникает, когда:

- Внутри одного визуального блока (`<p>`, `<div>`) слишком много `<br>`,
- а содержимое при этом не является структурой, где переносы действительно нужны (список/таблица).

### Правила

1. Парсить HTML через BeautifulSoup (уже используется в проекте).
2. Обходить кандидатов-блоки: `p`, `div`, `span` (по необходимости).
3. Пропускать блоки, которые содержат:
   - `ul/ol/li`, `table/tr/td/th`, `pre/code`
4. Для каждого блока считать количество `<br>`.
5. Если `br_count >= THRESHOLD` (например, 8–10), считать блок «сломленным» и:
   - заменить `<br>` на пробел
   - схлопнуть множественные пробелы
6. Не трогать одиночные/редкие `<br>` (чтобы не ломать «а) …<br>б) …»).

### Почему именно так

- Это минимально инвазивно: правим только явно аномальные случаи.
- Списки/таблицы/код остаются нетронутыми.
- Риск поломать корректные задачи существенно ниже, чем при удалении всех `<br>`.

## UX/Отображение

- UI остаётся прежним: шаблоны продолжают выводить HTML как `|safe`.
- Пагинация уже внедрена; нормализация контента не должна влиять на навигацию.

## Проверка корректности

- Подготовить небольшой набор примеров «до/после» (2–5 задач) с проблемным «столбиком».
- Проверить, что блоки вида «а) …<br>б) …» не превращаются в одну строку (за счёт порога).
- Проверить, что изображения (локальные `/media/...`) не ломаются.

## Риски и смягчение

- Риск: некоторые «нормальные» задачи с большим количеством `<br>` могут быть схлопнуты.
  - Смягчение: порог, исключения (ul/ol/table/pre), `--dry-run` и ограничение на батч.
- Риск: в редких задачах переносы внутри формул/MathML могут вести себя иначе.
  - Смягчение: обработка только `<br>`, без переписывания MathML.
