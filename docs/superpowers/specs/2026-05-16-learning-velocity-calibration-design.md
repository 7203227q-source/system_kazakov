# Дизайн: калибровка learning_velocity (темп обучаемости)

Дата: 2026-05-16

## Контекст

На дашборде ученика отображается показатель **Темп** `x{learning_velocity}` из `StudentSubjectProfile.learning_velocity`.
Сейчас он используется как множитель прогноза (`predicted_exam_score`) и не пересчитывается автоматически.

## Цель

Автоматически калибровать `learning_velocity` по результатам ученика так, чтобы:
- показатель адаптировался к реальным результатам (ученик лучше/хуже прогноза);
- **не было сильной волатильности** в начале (когда мало данных);
- **не было скачков** из‑за просрочек/пропусков дедлайна.

## Когда пересчитываем

- Пересчёт происходит **после завершения варианта** (`Assignment.is_completed=True`) в момент, когда у варианта есть итоговый результат (в процентах).
- Источники:
  - контрольные (`Assignment.is_verified=True`) — основной сигнал;
  - обычные варианты — добавочный сигнал (вес ниже), и/или подключается после “прогрева”.

## Что именно считаем (ошибка прогноза)

Для предмета/профиля ученика (subject):

- `predicted` — прогноз модели **на момент завершения варианта**:
  - берём из последнего `DailySnapshot.predicted_exam_score` по этому студенту и предмету **на дату ≤ даты завершения** (или на текущую дату, если нет точного совпадения).
  - если snapshot отсутствует — калибровку пропускаем.
- `fact` — фактический результат варианта в процентах 0..100:
  - `fact = 100 * (sum(primary_score по задачам варианта) / max_primary_score экзамена)`
  - использовать экзаменную шкалу `ExamScoreScale.max_primary_score` для данного `exam_format` профиля/варианта (если доступна).
  - если данных недостаточно (нет шкалы/нет submissions) — калибровку пропускаем.
- ошибка: `err = fact - predicted` (в процентах, может быть отрицательной).

Интерпретация:
- `err > 0`: ученик стабильно лучше прогноза → `learning_velocity` слегка увеличить.
- `err < 0`: хуже прогноза → `learning_velocity` слегка уменьшить.

## Правило обновления (плавность, без волатильности)

### Базовое изменение

- `delta = k * err / 100`
- рекомендуемое `k = 0.25` (можно вынести в константу).

### Ограничение шага

- `delta = clamp(delta, -0.10, +0.10)` (требование пользователя).

### Прогрев (warm-up) на старте

Чтобы избежать волатильности при малом числе работ:

- считаем `n` = количество уже учтённых калибровок (или количество “учтённых” вариантов за последние 30–60 дней).
- если `n < 5`: умножаем delta на 0.3
- если `5 ≤ n < 10`: умножаем delta на 0.6
- иначе: без коэффициента (1.0)

### Дедлайны: сильный штраф

Если вариант завершён после дедлайна или пропущен:

- если `assignment.due_date` задан и `completed_at_date > due_date`:
  - `deadline_weight = 0.2`
- если вариант помечен как `is_expired=True`:
  - `deadline_weight = 0.2`

Итоговый delta:
- `delta *= deadline_weight`

### Границы learning_velocity

Пользователь подтвердил: **0.5 .. 1.5**

- `learning_velocity = clamp(learning_velocity + delta, 0.5, 1.5)`

## Где хранить “учтённые калибровки”

Нужно избегать повторного пересчёта по одному и тому же варианту (переоткрытие/повторное сохранение).

Варианты реализации (выбрать 1):
1) Добавить поле на `Assignment`: `learning_velocity_calibrated_at` (datetime, null) — если не null, не калибровать повторно.
2) Добавить отдельную модель `LearningVelocityCalibrationLog(assignment, student, subject, err, delta, created_at)` — более прозрачно, но больше таблиц.

Рекомендуемый вариант: **(1)** как минимально инвазивный.

## Точки интеграции

- После завершения варианта в `student_solve_assignment` (и в авто‑expire, если он выставляет `is_completed=True`), выполнить:
  - вычисление `fact`
  - поиск `predicted`
  - расчёт delta с правилами выше
  - запись нового `learning_velocity` в `StudentSubjectProfile`
  - отметку, что вариант учтён для калибровки (см. раздел выше)

## Критерии готовности

- `learning_velocity` изменяется только после завершения варианта.
- При малом количестве данных изменения маленькие (warm-up).
- При завершении после дедлайна изменения сильно ослаблены (weight=0.2).
- `learning_velocity` всегда остаётся в диапазоне 0.5..1.5.
- Повторное открытие/сохранение варианта не приводит к повторной калибровке.
