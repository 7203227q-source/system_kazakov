# Точный ответ при регенерации задачи (без округления)

## Цель
При регенерации задачи через OpenRouter добиться того, чтобы `correct_answer` был:
- целым числом или конечной десятичной дробью;
- без принудительного округления (только точное значение, которое действительно является конечной десятичной записью).

## Проблема
Модель часто возвращает десятичное приближение (например, `0.2917`), даже если в тексте шаблона просим “без нецелых/периодических/иррациональных”. Код проекта не округляет `correct_answer` сам — он сохраняет строку, которую вернул провайдер.

## Требования
- При регенерации (preview/apply) модель обязана возвращать “точную форму” ответа, из которой сервер может однозначно получить конечную десятичную запись без округления.
- Если ответ не может быть представлен как конечная десятичная дробь (после сокращения знаменателя), preview должен показывать понятную ошибку и не применять изменения.
- Формат хранения в БД остаётся строковым `Task.correct_answer`.

## Предлагаемое решение (B)
### 1) Контракт ответа от модели
В JSON-ответе по-прежнему используются поля:
- `content_html`
- `solution_html`
- `correct_answer` (человеко-читаемая форма; допускается временно пустая)
- `notes` (служебное поле)

Добавляем обязательное правило:
- В `notes` модель должна вернуть `exact_fraction=<a>/<b>` (например, `exact_fraction=7/40` или `exact_fraction=123/1`).
- `a` и `b` — целые числа, `b>0`.
- Дробь должна быть сокращена (для простоты проверки), либо сервер сокращает сам.

### 2) Серверная валидация и получение `correct_answer` без округления
На backend добавляется функция:
- достаёт `exact_fraction` из `notes`;
- парсит `a/b`;
- сокращает дробь через `gcd`;
- проверяет, что после сокращения знаменатель имеет только множители 2 и 5 (тогда десятичная запись конечна);
- строит десятичную строку без округления:
  - если знаменатель 1 → целое `a`;
  - иначе приводит знаменатель к виду `10^k` домножением на 2/5 и формирует строку с нужным числом знаков после запятой;
  - убирает хвостовые нули и точку (пример: `0.2500` → `0.25`, `12.000` → `12`).

Если `exact_fraction` отсутствует/некорректен/не даёт конечной десятичной записи:
- preview/apply возвращают ошибку (preview может показать исходное содержимое как fallback, но с `error`).

### 3) Усиление prompt
Даже если в UI введён свой шаблон, сервер добавляет в prompt “технический хвост” с правилами:
- вернуть строго JSON;
- в `notes` вернуть `exact_fraction=a/b`;
- `correct_answer` тоже должен быть конечной десятичной дробью или целым;
- запрещено округлять/приближать; если получается не конечная десятичная — нужно изменить числа задачи.

## Изменения в точках кода
- OpenRouter prompt: `core/openrouter_client.py::generate_task_regeneration`
- Валидация и нормализация результата регенерации:
  - либо отдельный helper в `core/services_openrouter.py`,
  - либо утилита в новом модуле `core/answer_format.py` (предпочтительно для тестирования).
- Views: `core/views.py::admin_task_regen_preview` и `admin_task_regen_apply` должны использовать нормализованный `correct_answer`, а не “как пришло”.

## Ошибки и UX
- В preview при ошибке показываем:
  - `error`: человеко-читаемое сообщение, например: “ИИ вернул не конечный десятичный ответ. Попросите изменить числа.”
  - содержимое можно оставить как у задачи-оригинала (как сейчас), чтобы админ не видел пустой блок.
- В apply при ошибке: `400` и `{error: "..."}`

## Тестирование
- Unit-тесты утилиты конвертации `a/b` → точная десятичная строка:
  - `7/40` → `0.175`
  - `10/4` → `2.5` (с сокращением)
  - `1/3` → ошибка (не конечная)
  - `2/1` → `2`
  - `-7/40` → `-0.175`
- Тест view (минимальный): мокнуть `generate_task_regeneration` так, чтобы вернуть `notes` с `exact_fraction`, и проверить, что preview/apply отдают/сохраняют именно нормализованный `correct_answer`, а не “0.2917”.
